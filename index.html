AI 완료 보고 점검기

이 앱은 AI에게 일을 맡기고 '완료했다'는 보고를 받는 사람이, 그 보고를 한 번 더 점검하고 그 점검이 실제로 맞았는지 점수로 재 보도록 돕습니다.

논문의 어느 결과를 쓰나요(한 문장으로 자세히)

이 앱은 AI에게 일을 맡기고 '완료했다'는 보고를 받는 사람이, 논문의 재검토 방식(결과는 고치지 않고 확신도와 검토 필요 여부만 다시 받기)으로 그 보고를 한 번 더 점검하고, 논문 3.4절의 균형정확도로 그 신호가 실제 오류를 얼마나 가려냈는지 내 기록으로 재 보도록 돕습니다.

1 점검하기

AI가 "다 했다"고 한 일이 믿을 만한지 점검합니다.

  1. 넣기 원문(시킨 내용)과 AI가 낸 결과를 아래 두 칸에 붙여 넣기
  2. 바로 대조 [자동 원문 대조]로 숫자·기호·항목이 빠지거나 바뀌었는지 보기(AI 없이 즉시)
  3. 한 번 더 점검(선택) 앱이 만든 문장을 다른 AI에게 붙여 시키고 → 그 AI의 답을 2단계로 가져오기
처음이라면
어려운 말 풀이
  • 프롬프트: AI에게 시킬 문장. 앱이 만들어 주니 복사해서 붙이면 됩니다.
  • JSON: AI가 돌려주는 답의 모양. 복사해서 2단계에 붙이면 앱이 알아서 읽습니다.
  • 균형정확도: 틀린 걸 잡아낸 비율과 맞는 걸 건드리지 않은 비율의 평균. 높을수록 점검이 믿을 만합니다(논문 3.4절의 계산법).
  • Brier 점수: AI가 말한 확신도가 얼마나 정확했는지. 낮을수록 좋습니다.
  • MCP: AI 도구가 다른 기능을 불러 쓰는 공통 방식. 설치형 연결은 "연결" 탭에 있습니다.
다른 AI에게 시킬 문장(복사해서 붙이기)

      다른 AI 도구에서 복붙 없이 쓰는 법입니다. 모두 내 컴퓨터 안에서만 돌고 키·이메일이 필요 없습니다.

      어떤 방법을 고를까요 (가장 쉬운 방법은 설치 없이 이 화면에서 붙여넣기)
      방법이럴 때준비물
      이 화면가끔 붙여넣기로 충분할 때브라우저
      주소로 열기브라우저 에이전트가 주소만 열어 결과를 읽게 할 때브라우저
      MCPClaude Code·Desktop·Codex 안에서 말로 시킬 때Node.js, 앱 ZIP
      내 컴퓨터 API직접 만든 프로그램에서 호출할 때Node.js, 앱 ZIP
      1단계 공통 준비(Node.js와 폴더)
      1. 터미널(Windows는 PowerShell)에서 node -v 를 입력해 v18 이상이 나오는지 봅니다. 없으면 nodejs.org 에서 LTS를 설치하세요.
      2. 앱 ZIP(review_signal_app.zip)을 새 폴더에 풀고, 그 폴더의 전체 경로를 복사해 둡니다(아래 폴더경로 자리에 씁니다).
      3. 시험: 그 폴더에서 node --test tests/logic.test.js tests/check.test.js tests/mcp.test.js tests/keys.test.js 가 모두 통과하는지 봅니다.
      MCP로 AI 도구에 연결하기

      MCP는 AI 도구가 외부 기능을 부르는 공통 방식입니다. 등록해 두면 AI에게 말로 시킬 수 있습니다.

      Claude Code

      claude mcp add --transport stdio review-signal -- node 폴더경로/mcp/server.mjs

      Claude Desktop

      claude_desktop_config.json 의 mcpServers 에 넣고 앱을 다시 켭니다(Windows 경로는 역슬래시를 두 개씩).

      {
  "mcpServers": {
    "review-signal": { "command": "node", "args": ["폴더경로/mcp/server.mjs"] }
  }
}

      Codex

      ~/.codex/config.toml 에 추가합니다.

      [mcp_servers.review-signal]
command = "node"
args = ["폴더경로/mcp/server.mjs"]

      잘 연결됐는지 확인

      review-signal 도구의 verify_completion 으로 아래 두 글을 점검해 줘.
[원문] B#2 값 0.9685245400, 허용 오차 ±0.5
[결과] B#2 0.96852454, 허용 오차 0.5 — 모두 완료

      "소수 자릿수 손실", "기호 누락", "완료 주장과 불일치"가 나오면 성공입니다. 도구: verify_completion(한 번에 점검), check_against_source, build_review_prompt, parse_review_json, score_review_signal, paper_models, 프롬프트 verify-completion.

      시험 상태: 직접 만든 요청으로 연결 과정과 도구 호출 응답은 확인했지만, 위 세 앱에 실제로 등록해 본 시험은 하지 못했습니다. 안 되면 경로(공백은 따옴표)를 먼저 확인하세요.

      내 컴퓨터 API로 부르기

      이 컴퓨터(127.0.0.1)에서만 열리고 서버가 필요 없습니다.

      1. 서버를 켭니다(창은 닫지 마세요, 끄려면 Ctrl+C): 
        node mcp/server.mjs --http 8787
      2. 다른 터미널에서 확인: 
        curl http://127.0.0.1:8787/health
      3. Windows PowerShell에서 점검 요청: 
        $body = @{ requirement = "B#2 값 0.9685245400"; result = "B#2 0.96852454 — 모두 완료" } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8787/api/verify `
  -ContentType "application/json; charset=utf-8" `
  -Body ([System.Text.Encoding]::UTF8.GetBytes($body))
      4. macOS·Linux: 
        curl -s -X POST http://127.0.0.1:8787/api/verify -H "Content-Type: application/json" \
  -d '{"requirement":"B#2 값 0.9685245400","result":"B#2 0.96852454 — 모두 완료"}'

      주소: POST /api/verify(원문 대조+재검토 프롬프트), /api/check, /api/prompt, /api/parse, /api/score, GET /api/models, GET /health

      API 키

      인터넷 주소로 어디서나 부르는 API용 키입니다. 아직 서버가 없어 키를 발급하지 않습니다.

      어떻게 동작하나요
      1. 이메일 형식과 가짜 주소를 점검합니다(공백·잘못된 형식, 일회용·예시·테스트 도메인, 임시로 만든 듯한 이름). 지메일의 점·별칭 변형은 같은 사람으로 봅니다.
      2. 서버가 그 도메인이 메일을 받을 수 있는지 확인하고 인증 메일을 보냅니다. (이 단계는 서버가 연결돼야 동작합니다.)
      3. 메일의 링크를 눌러야 키가 한 번 보입니다(30분 안, 링크는 한 번만). 서버에는 키의 해시만 저장하고, 같은 사람이 다시 받으면 이전 키는 폐기됩니다.
      4. 요청이 몰리지 않게 이메일당 시간당 3번, 같은 접속지당 10번으로 제한합니다.

      가짜 이메일을 완벽히 걸러낼 수는 없습니다. 실제로 확인되는 것은 인증 메일의 링크를 누른 사람뿐입니다. 로컬 MCP·API는 키가 필요 없고, 이 키는 인터넷에 열린 서버가 생겼을 때만 의미가 있습니다.

      개발자: 서버 연결 방법

      발급 로직(이메일 점검, 인증 링크, 키 해시 저장, 사용 제한, 키로 보호되는 /v1/verify·/v1/check·/v1/score)은 keys/ 에 만들었고 개발 서버와 가짜 시계로만 시험했습니다(실제 메일 서비스·호스팅과는 연결해 보지 못했습니다). 서버만 비어 있습니다. 로컬에서 확인: node keys/dev-server.mjs(메일은 /dev/outbox 에 쌓임). 서버에 올릴 때는 저장소를 KV/DB로, 메일을 실제 메일 서비스(resendMailer)로 바꾸고 config.js 의 REVIEW_SIGNAL_API_BASE 에 서버 주소를 넣으면 이 칸이 켜집니다. 자세한 순서는 keys/README.md.

      논문·한계

      왜 이렇게 만들었나

      논문의 출발점은 AI가 테스트 통과를 '완료'라고 보고했는데 다시 물으면 일부만 했다고 답하거나, 다른 LLM의 원문 대조에서 기호 오독·소수 자릿수 손실·내용 누락이 나온 개발 경험입니다. 논문은 이 경험을 재현하지 않고, 합성 문제 12개에서 '검토 요청 표시'가 실제 오답과 맞는지만 쟀습니다. 이 앱은 그 측정 방식을 내 작업에 옮겨 쓰게 합니다.

      논문에서 가져온 것
      • 프로토콜(3.3절, 부록 B1): 최초 결과는 고치지 않고, 정답·채점 피드백 없이 확신도와 needs_review만 다시 받는다.
      • 계산식(3.4절): 균형정확도 = (오답 검토율 + 1 − 정답 검토율) / 2, Brier. 정답이나 오답이 없으면 계산하지 않습니다.
      • 비교 숫자: 표 1·2의 OpenAI 7종·Claude 4종. OpenAI 값은 T03 경로 표기를 사후 보완해 채점한 값이고 Claude 값은 보완 방식을 실행 전에 고정한 값입니다. 제공자별 실행 환경이 다르고 모델당 12문항 1회라서 순위로 읽지 마세요. 논문은 같은 모델이 자기 답을 다시 평가한 경우만 다뤘기 때문에 비교 막대는 '같은 AI' 기록에만 씁니다.
      • 사례: 4.2·4.3절과 부록 A.
      앱이 추가한 것(논문에 없음)

      자동 원문 대조와 자동 신호, 근거 유형(reason_type), 재검토한 쪽 구분, 확신도 20 이하 표시, 흔들림 범위(윌슨 구간), 점수 구간 해석(90%·70%), MCP·API·키 발급.

      한계

      논문은 합성 문제 12개의 탐색 연구이고 정답률과 검토 요청의 일반적 관계를 확정하지 못했습니다. 이 앱의 점수는 내가 직접 확인한 기록에만 의존하고 오답이 적으면 크게 흔들립니다. 자동 원문 대조는 글자 수준만 봅니다. 논문과 이 앱은 AI의 도움을 받아 썼습니다(논문: 연구자 alska14의 경험과 주제 선택을 바탕으로 AI가 실험 실행·분석·집필을 보조).
